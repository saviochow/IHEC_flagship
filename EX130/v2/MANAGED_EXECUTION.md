# EX130 v2: governed execution and figure handoff

This is a non-authorizing integration adapter around the immutable EX130 v2 analysis bundle at review commit 176a7aeb49ba0f7bf0050ff0340451baf5c47dd0. It does not change the discovery or validation algorithm. The archive source and both embedded analysis files are independently pinned: the latter SHA-256 values were read from the existing Yipcluster staged copy. The existing 358-record sample manifest is also pinned by its observed digest. No human data or result files are committed here.

## Why a managed adapter is required

The existing raw allocation launcher needs V2_SOURCE_ROOT and V2_RUN_ROOT from the interactive shell. Researchstack submits with --export=NONE and invokes the reviewed payload through deploy/job_runtime.py, which supplies RESEARCHSTACK_CONTEXT, RESEARCHSTACK_RUN_DIR and RESEARCHSTACK_TASK_DIR. The managed adapter embeds the exact scientific source and launcher in the payload, explicitly sets site-specific input paths and interpreter, and uses task-0/ex130-v2 for new outputs. It avoids depending on a mutable remote checkout or caller shell exports. The canonical Researchstack runtime and separate site admission/approval remain the authority.

First reconstruct the immutable bundle as documented in EX130/v2/README.md. Run the existing and additional synthetic tests with python3 -m unittest discover -s EX130/v2/tests -v. Then, with an independently reviewed private JSON configuration containing exactly cluster, ex130_root, logits_dir, gff, features_root, python, source_model, workers, manifest_sha256, run:

    python3 EX130/v2/managed_payload.py --source-dir EX130/v2 --config PRIVATE_CONFIG.json --output NEW_PAYLOAD_DIR

The exact manifest digest is 411a795141301a87888175430ffd4248e497bc3133023434ed36921a74b004f7. The configuration is not a Researchstack plan. The payload renderer creates payload.sh and payload_receipt.json, no proposal or approval. A real plan must bind the payload digest, actual dataset and environment identities, evaluator/protocol digests, reviewed source revision, exact helper/runtime hashes, complete verified Storage manifest, requested allocation and independent validator/human evidence. No dummy digest may authorize a real job.

## Current scheduler and storage blockers

The live ClusterMCP scheduler gateway was disabled/unreachable at audit; the IHEC repository is not in its managed repository allowlist and the science catalog has no enrolled profiles. Researchstack currently permits Yipcluster only as approved overflow with fresh Pines resource-pressure evidence and requires its results to be on the verified Pines-backed pines_mount view. EX130 inputs and staged source are currently in Yipcluster-local locations. The ClusterMCP-approved Yip scratch work root and Researchstack's existing storage contract do not agree. Resolve that explicitly in reviewed deployment policy; do not fabricate pressure, substitute a local scratch marker or bypass the managed scheduler. For a Yip data-local workload, any change to site selection needs independently approved policy and validation. The current Pines mount and boot unit can be preserved without a reboot.

## Result verification

The payload preserves incomplete outputs and creates task-0/ex130_artifact_manifest.json with case completeness and explicit PNG/SVG, receipt and review-table hashes and sizes. It does not include the expression cache or per-sample feature tables in the artifact inventory. All remain on private research storage. The manifest is not a signed receipt or proof of job settlement: verify the journal-bound Slurm status, accounting and actual files separately. EMPTY_DISCOVERY is an explicit result, not evidence of a positive or negative example. Do not interpret a validated feature contrast as causal attribution or absence of absolute feature change: the original stable control tests the within-gene contrast. Inspect per-transcript levels and raw genomic tracks before selecting paper examples.

ClusterMCP can read bounded text metadata and SVG files where within policy; native binary artifact retrieval requires an explicitly enrolled delivery capability or existing authorized SCP. Never tunnel arbitrary binary/private measurement files through the text interface or publish them in GitHub. No root setup, new credentials, scheduler submissions or service restarts are part of this adapter.

It runs the actual generated managed payload against disposable synthetic expression and feature inputs, supplying only a mocked runtime envelope, exercising positive/negative discovery, real PNG/SVG rendering, manifest verification and refusal of duplicate execution. Matching the Python minor version and plotting dependencies does not prove exact patch compatibility or complete environment identity or actual Slurm execution. The MCP client remains a separate newer Python environment. All real site-policy and independent approvals remain required.
